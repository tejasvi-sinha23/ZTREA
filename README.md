# Secure File Notary CLI

A Python-based digital signature toolkit that lets you sign files, verify their integrity, and send cryptographically signed messages over a local network — with built-in replay attack protection.

---

## Features

- **RSA Key Generation** — generate a 2048-bit RSA key pair saved as PEM files
- **File Signing** — sign any file with your private key; produces a `.sig` file
- **Signature Verification** — verify a file hasn't been tampered with using the public key
- **Signed Network Messaging** — client/server pair that exchanges signed, timestamped messages
- **Replay Attack Protection** — server rejects messages older than 30 seconds

---

## Project Structure

```
Secure File Notary CLI/
├── notary.py          # CLI tool: keygen, sign, verify
├── client.py          # Network client — signs and sends messages
├── server.py          # Network server — verifies signatures and enforces freshness
├── private.pem        # RSA private key (generated by keygen)
├── public.pem         # RSA public key (generated by keygen)
├── contract.txt       # Example file to sign
└── contract.txt.sig   # Example signature file
```

## Usage

### 1. Generate Keys

Creates `private.pem` and `public.pem` in the current directory. Will refuse to overwrite existing keys.

```bash
python notary.py keygen
```

---

### 2. Sign a File

Signs a file using your private key and saves the signature as `<filename>.sig`.

```bash
python notary.py sign contract.txt
```

Using a custom key path:

```bash
python notary.py sign contract.txt --key /path/to/private.pem
```

---

### 3. Verify a File

Verifies that a file matches its signature and hasn't been altered.

```bash
python notary.py verify contract.txt contract.txt.sig
```

Using a custom public key:

```bash
python notary.py verify contract.txt contract.txt.sig --key /path/to/public.pem
```

Output examples:

```
[+] VERIFIED: The file is authentic and unaltered.
[-] FAILED: The signature is invalid. The file has been tampered with or the wrong key was used.
```

---

### 4. Signed Network Messaging

The client signs a message (with a timestamp embedded in the payload) and sends it to the server. The server verifies both the cryptographic signature and the message age.

**Start the server first:**

```bash
python server.py
```

**Send a signed message from the client:**

```bash
python client.py
```

**Simulate a replay attack** (the client artificially ages the timestamp by 60 seconds):

```bash
python client.py --replay
```

Expected server output for a valid message:

```
[+] VERIFIED: 'AUTHORIZE TRANSFER: $500 to Account A' (Age: 1s)
```

Expected server output for a replayed message:

```
[-] BLOCKED: Message is 60 seconds old. Replay attack detected.
```

## How It Works

### File Notary (`notary.py`)

1. **Key generation** — uses RSA with a 65537 public exponent and 2048-bit key size.
2. **Signing** — reads the file as raw bytes, signs with RSA-PSS + SHA-256, and saves the base64-encoded signature.
3. **Verification** — decodes the signature and runs `public_key.verify()`. Any byte-level change to the file will fail verification.

### Client / Server

- The client builds a JSON payload containing the **message** and a **Unix timestamp**, then signs the entire payload — not just the message. This prevents an attacker from swapping in a fresh timestamp on an old, intercepted message.
- The server performs two checks in order:
  1. **Cryptographic check** — verifies the RSA-PSS signature against the public key.
  2. **Temporal check** — rejects any message whose timestamp differs from server time by more than `MAX_TIME_DRIFT` (default: 30 seconds).

---

## Security Notes

- `private.pem` is stored unencrypted. In production, protect it with a passphrase or a secrets manager, and never commit it to version control.
- The replay window (`MAX_TIME_DRIFT = 30s`) assumes client and server clocks are roughly in sync. For production use, consider NTP synchronization.
- This project is designed for learning and local demonstration. It is not a production-grade PKI system.
